# DocInsight working agreement

Read `docs/CURRENT_STATE.md`, `docs/HANDOFF.md`, `docs/DECISION_LOG.md`, relevant ADRs, and the current repository state before resuming work. Read `DocInsight_SRS_Architecture.md` before proposing implementation. Reconcile documentation with code rather than assuming either is current.

The project owner makes technical and product decisions. Follow **Inspect → Explain → Propose → Obtain the owner's decision → Implement the approved scope → Verify → Document → Review**. The target is the full specification MVP (all P0 requirements); no P0 deferral is approved. There is no fixed delivery deadline. An intermediate working slice is not the completed MVP.

Before each implementation package, provide its ID, objective, requirement IDs, approved and unresolved decisions, expected files, included and excluded behavior, acceptance criteria, verification, dependencies, risks, and effort estimate. Wait for package approval. Approval of a package does not approve unresolved choices; “continue” applies only to the currently approved scope. Do not install dependencies, scaffold, migrate, implement, use paid providers, deploy, push, publish, delete existing work, or delegate to sub-agents outside an approved scope or explicit owner instruction. Ask before destructive operations. Routine fixes within an approved design do not need line-by-line approval.

Present meaningful decisions with options, recommendation, tradeoffs, code/product consequences, and a specific choice. Record statuses as `proposed`, `approved`, `rejected`, `superseded`, or `deferred`. Record approval using the owner's actual instruction; do not invent dates, quotations, reasons, results, or metrics. Pause affected work if an unexpected issue needs an architectural change.

Explain each new component before introducing it: purpose, inputs/outputs, ownership, dependencies, integration, failures, and verification. For Django, distinguish models, serializers, views, services, and tasks. For React, distinguish local and server state and justify hooks, effects, polling, cleanup, and caching. Keep packages small and document actual symbols and paths after implementation.

Maintain `docs/UNDERSTANDING_CHECKPOINTS.md`: every optional understanding checkpoint must include its question and a plain-English answer, package/topic, relevant implementation references and limitations. Add it during the same package or explanation session, not just in chat. Keep checkpoints optional. Backfill earlier recoverable prompts without inventing historical quotations. Update answers when decisions/code change, distinguish planned from implemented behavior, and link from interview/package notes rather than duplicating full answers.

Keep private file access, user isolation, citation integrity, and source provenance visible. Label fixtures and fake providers as simulated. Keep secrets out of source, docs, logs, and browser bundles; use synthetic or openly usable demonstration documents. Do not call paid providers before approval of provider and budget. Never infer semantic support solely from a structurally valid citation.

Update relevant documents with each approved package, especially requirement traceability, development log, current state, and handoff. Report what changed, how it works, actual files and symbols, commands and results, incomplete work, documentation, and the next proposed package. Do not claim checks or features that were not completed. Before ending a development session, leave an exact resume point in `docs/CURRENT_STATE.md` and `docs/HANDOFF.md`.
